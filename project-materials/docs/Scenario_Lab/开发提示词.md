## 1. 产品目标

让研究者从一段简短的两难冲突情景描述出发，经过可编辑剧本、生产 prompt、首尾关键帧审核、视频生成和质量检查，最终得到三条可以用于互动体验的成品视频：

1. `Conflict Scenario Video`：呈现两难冲突本身，在选择发生前结束，不替参与者作决定。
2. `Choice A Consequence`：呈现机器人执行 Choice A 后产生的直接后果和未被满足一方的反应。
3. `Choice B Consequence`：呈现机器人执行 Choice B 后产生的直接后果和未被满足一方的反应。

三条视频合称一个 `Video Bundle`。

研究者必须在每个关键阶段保有控制权：

- 可以编辑 AI 生成的研究者友好剧本；
- 可以查看但默认折叠长 prompt；
- 可以逐张评论并只重生成某一张关键帧；
- 可以提交 general comment，修正全局问题并创建一个新的完整生产版本；
- 必须审核并批准全部关键帧后，才能提交付费视频生成；
- 可以对生成的视频进行 QA、拒绝某个片段并基于失败证据局部重生成；
- 所有已经提交过的 prompt、图片和视频都必须保留版本及来源记录，不得被静默覆盖。

## 4. 核心概念：三条最终视频与内部 production clips

最终输出始终只有三条研究视频，但每条 15 秒左右的最终视频可以由 1–3 个 `Production Clip` 组成。不要在界面或数据结构中把 production clip 误叫成第四条、第五条 outcome video。

AI 必须先通过 complexity gate 决定每条最终视频采用：

- 单个连续 clip；或
- 2–3 个更可控的 clips，最后在服务端进行 trim、拼接、音频衔接和转码。

默认总时长为 15 秒；允许研究者在合理范围内修改。每个 clip 必须有自己的：

- 时长和在最终视频中的时间区间；
- 单一叙事目的；
- attention owner；
- camera state / camera move；
- 对话和音频预算；
- T2V、I2V 或 FLF2V mode；
- 首帧和可选末帧规格；
- 长视频生成 prompt；
- QA contract；
- 生成任务与版本记录。

优先采用以下制作原则：

- 一条最终视频最多三个 production beats / clips；
- 一个 clip 只承载一个主要可见动作；
- camera move 自己占一个 beat，不与跌倒、碰撞、抓取、情绪崩溃等 P0 动作同时发生；
- 如果严格的镜头顺序很重要，使用分 clip 制作或候选筛选，不要声称时间戳 prompt 能保证确定性；
- 当一个人物已经离开镜头，可通过画外音和环境音保持另一方的竞争性请求，避免来回反打和重复 pan；
- 如果 provider 只支持固定时长，生成固定时长素材后在服务端确定性 trim，再拼接为最终约 15 秒视频；不要把 provider 限制泄漏成混乱的研究者界面。

### 剧本生成规则

- 这是给研究者读和改的内容，不是视频模型 prompt；语言清楚、简洁、无冗长技术指令。

- 不添加原始 scenario 没有支持的重大危险、伤害、人物或剧情反转。
- 对话必须服务研究含义，并为 15 秒内的自然表达留出足够时间。
- 对人物情绪使用研究者友好的词汇；详细的面部、呼吸、姿态载体放到后续 production plan。

### 7.3 优先级和复杂度规则

固定优先级：

```text
P0：决定故事含义的人物动作和情绪
P1：注意力竞争、选择含义、说话者意图和后果
P2：镜头路径、blocking 和可读景别
P3：身份、服装、空间、道具和机器人双手连续性
P4：灯光细节、材质、氛围和装饰性完成度
```

低优先级不得削弱高优先级。遇到冲突时，先简化 P4/P3/P2，再考虑改变 P0/P1，并向研究者显示 warning。

每个 P0 动作必须写完整动作链；每个 P0 情绪必须转成可观察的脸部、身体/呼吸、声音载体和持续规则。不能只写 “sad”“angry”“frightened”。

### 7.4 Prompt 编译规则

每个 clip 的长 prompt 按以下顺序编译：

1. P0 人物、完整动作和可观察情绪表现；
2. mode 和首/末帧的权责；
3. 带时间范围的可见 beat 和唯一主要 camera transition；
4. 对话、呼吸、哭声和环境音；
5. 第一视角与保护研究含义所必需的 continuity locks；
6. 简短的 hard invariants 和 exclusions。

必须同时使用正向替代行为和关键禁止项，例如：

```text
The child remains seated with both hands on their lap; they never stand or approach the lens.
```

不要生成字幕、对话气泡、按钮、logo 或任何网页 UI。字幕和互动控件属于网站层。

自然英语的初始语速参考为 2.5–3.2 words/second。儿童、哭泣、愤怒、惊慌、停顿和口型同步需要更多时间。超过预算时先缩短台词，不要用 “fast but natural” 掩盖物理上不可能的台词长度。

### 7.5 页面呈现

- 用卡片显示每条最终视频和内部 clips 的时间线；
- 显示 mode、时长、attention owner、camera path、dialogue budget、warnings；
- production prompt 默认折叠；点击 `View full prompt` 展开；
- 展开后允许高级研究者编辑，但编辑后必须创建新 prompt version；
- 显示每个 prompt 的 version、parent version 和 last edited by；
- blocking issue 未解决时不允许进入关键帧生成；
- 提供 `Recompile this video` 和 `Approve production plan`。

## 8. 阶段 04：Keyframes Review

### 8.1 关键帧生成原则

- I2V：必须有严格首帧；
- FLF2V：必须有兼容的首帧和末帧；
- T2V：没有图像锚点，但如果当前研究流程要求视觉 continuity，可由 AI 建议切换到 I2V；
- 使用精确 16:9；首选 1920×1080 PNG；
- 图片负责人物外观、构图、身份、空间、灯光、机器人手和时间零/终点状态；
- `public/inattentive-assets/scenario-02.png` 是机器人双手的强制主参考，不是普通的可选 style reference；每次生成包含机器人双手的关键帧时都必须作为 image/reference input 传入（按 active provider 的真实 reference-image 能力实现）；
- 参考图只锁定画面下方机器人双手的形态、材质、配色、关节结构、前臂比例、透视和大致屏幕位置，不要求复制参考图中的老人、快递员、门厅、雨天或其他环境内容；
- 视频 prompt 负责动作、顺序、时间、camera path、声音和状态变化；
- 首末帧之间必须能通过一个物理上连续的镜头或动作连接；如果必须 teleport、隐藏 cut 或同时执行多个关键动作，应改 mode、拆 clip 或重做关键帧。

### 8.2 图片生成 AI 输入

每一张图片的生成请求必须包含：

```json
{
  "scenarioId": "string",
  "bundleVersion": "string",
  "videoType": "string",
  "clipId": "string",
  "frameRole": "first | last",
  "frameSpec": "当前 production package 中的结构化规格",
  "globalContinuityLocks": {},
  "characterReferences": [],
  "roomReferences": [],
  "robotReference": [
    {
      "assetPath": "/inattentive-assets/scenario-02.png",
      "role": "mandatory_robot_hands_shape_position_reference",
      "scope": "copy only the two robot hands and forearms; ignore people and environment"
    }
  ],
  "adjacentApprovedFrames": [],
  "styleReferences": [],
  "negativeConstraints": [],
  "revision": {
    "parentFrameId": "string | null",
    "researcherComment": "string | null",
    "retain": [],
    "change": []
  }
}
```

### 8.3 图片生成输出

每张图片保存：

```json
{
  "frameId": "string",
  "assetUrl": "string",
  "width": 1920,
  "height": 1080,
  "promptVersion": "string",
  "generationTaskId": "string",
  "parentFrameId": "string | null",
  "sha256": "string",
  "status": "generated | approved | rejected | failed",
  "createdAt": "ISO timestamp"
}
```

不要把大型 base64 图片和视频塞进 localStorage。使用服务端 asset storage/provider URL 和轻量 metadata；通过 storage adapter 隔离实现，方便以后迁移到持久化云存储。任何 API key 只保存在服务端环境变量中。

### 8.4 关键帧界面

显示所有三条视频、所有 clips 的全部首/末帧。每张卡片至少有：

- Video / Clip / First or Last 标记；
- 大图预览和全屏查看；
- version；
- generation status；
- frame prompt（默认折叠）；
- `Approve`；
- `Reject`；
- 单张 comment 输入框；
- `Regenerate this frame`。

页面同时提供一个明确区分的 `General revision` 区域，用于处理：

- 三条视频共有的人物身份或服装问题；
- 房间布局不连续；
- 机器人双手的数量、造型、颜色、方向、比例或位置不一致；
- 全局镜头方向或轴线错误；
- 所有 prompt 的共同问题；
- 整个剧本/分镜层面的共同问题。

点击 `Apply general revision` 时：

1. 显示影响范围预览；
2. 默认创建新的完整 bundle version；
3. 将 comment 编译为明确的 `retain` 和 `change`；
4. 保留不受影响的研究者剧本内容；
5. 如果 comment 会改变研究含义或台词，先显示 script diff，并要求确认；
6. 重新编译受影响的 production packages；
7. 重新生成所有受影响的关键帧；
8. 旧版本图片仍可查看和恢复；
9. 不自动提交任何付费视频任务。

单张重生成只允许改变被评论的 frame layer：必须把当前图、相邻已批准图、全局 locks、研究者 comment、`retain` 和 `change` 一起发给 AI。其他图片和已批准剧本不得变化。

### 8.5 付费生成前强制 Anchor Gate

每一对实际 raster anchors 必须通过：

1. Silent-story test：隐藏 prompt，仅看首末帧也能理解变化；
2. Thumbnail test：缩至 25% 后，关键动作后果和情绪仍清楚；
3. Intensity test：P0 终点情绪达到 performance contract 的 0–5 目标；
4. Shot-scale test：依靠面部表达时，脸部应足够大；参考值为画面高度约 12% 或以上；
5. Contradiction test：需要哭泣、惊慌、痛苦或愤怒时，不能出现干眼、放松嘴型、对称休息姿态或中性表情；
6. Persistence test：需要持续到结尾的情绪必须在末帧仍保持；
7. Transition test：首末帧支持一个真实连续路径，P0 动作不藏在 camera transition 中；
8. Robot-hands test：两只机器人手在首末帧中的数量、身份、配色、比例和屏幕位置连续，无第三只手、无人体手、无形变；并与 `scenario-02.png` 下方双手在形态、白色外壳、黑色关节/掌部机械结构、五指关节、前臂透视和 lower-left/lower-right 构图上足够相似。

如果 safety restriction 无法产生所需的儿童情绪/动作关键帧，不得偷偷换成削弱 P0 的中性图。应向研究者显示原因，并明确选择：安全但仍清晰的 aftermath、I2V、拆 clip、授权参考图或后期确定性处理。不要对已知相同的安全拒绝概念进行无意义重复提交。

所有必须帧通过自动检查并被研究者手动批准后，`Generate videos` 才能启用。


### 9.4 页面内容

- 每条最终视频一个进度卡；
- 展示其内部 clips 的 queued/running/succeeded/failed；
- 支持页面刷新后的恢复；
- 单个 clip 失败不会丢失其他成功 clips；

- 保留每个 provider master；
- 按 assembly plan 进行 trim 和顺序拼接；
- 处理必要的 room tone、音量一致性和短音频衔接；

- 生成 1920×1080、H.264 High、yuv420p、AAC stereo、MP4 fast-start 的 web derivative；
- 保存最终 master、web derivative、每个源 clip、hash 和 assembly manifest；
- 任何已接受成品被替换前先保存旧版本。

最终命名遵循：

```text

scenario-{id}-choice-a.mp4
scenario-{id}-choice-b.mp4
```

### 10.1 自动技术检查

至少检查：

- 实际时长；
- 宽高和比例；
- 帧率；
- video/audio codec；
- audio channel count；
- 文件可完整解码；

### 10.2 时间线 QA

对每个源 clip 和最终拼接视频生成 contact sheet，并在 P0 trigger、动作轨迹、后果、情绪 onset/peak、台词中点、最后一个词和 final frame 附近密集采样。

```json
{
  "videoId": "string",
  "technicalPass": true,
  "checks": [
    {
      "requirementId": "R1",

      "severity": "critical | tolerable"
    }
  ],
  "audioReview": [],
  "finalVerdict": "accept | reject | researcher_review"
}
```

研究者必须能播放完整视频、逐帧/跳时查看、阅读 QA contract，并对每个问题记录 timestamped comment。

### 10.3 接受规则

自动拒绝：

- 任意 P0 动作或情绪不成立；
- 任意 P1 分支含义、说话者或后果错误；
- 人物位置交换、身份变化、第三只手、人体手或机器人手严重形变；
- 不是机器人第一视角；
- 对机器人说话时明显不看镜头；
- camera cut 代替被声明为严格的连续转动；
- 必需人物缺失；
- 音频不可用或说话者严重错误；
- 最终拼接顺序错误。

可人工判断的轻微问题：

- 不改变研究含义的轻微措辞变化；
- 轻微口型误差；
- 很小的背景道具漂移；
- 不影响 P0/P1 可读性的灯光或材质差异。

拒绝某个 clip 后，创建 revision delta：

```json
{
  "failureEvidence": [
    { "time": 5.5, "layer": "camera", "severity": "critical", "observation": "hard cut instead of pan" }
  ],
  "retain": ["identity", "dialogue order", "room", "accepted emotion"],
  "change": ["one continuous visible pan through the same room"]
}
```

重新编译完整 prompt，但只改变失败 layer。不得在旧 prompt 末尾无限追加修正，也不得覆盖生成过视频的历史 prompt。

### 10.4 Export / Publish-ready bundle

QA 全部通过后允许：

- 标记三条视频为 accepted；
- 下载三条 web MP4；
- 下载 production manifest / JSON；
- 将 bundle 连接到 Experience Port 的 scenario data；
- 生成网站层字幕/VTT 和对话时间数据（不要烤进视频）；
- 更新 asset cache version；
- 保持旧 accepted bundle 可回滚。

发布到 Experience Port 是单独的显式动作，不能在“视频生成成功”时自动发生。

## 11. Comment 与重生成的精确行为

### 单张图片 comment

输入：当前图片、该图片 prompt/spec、相邻关键帧、全局 continuity locks、comment、旧版本失败证据。

输出：只生成一张新图片和一条 revision record。不得修改剧本、其他图片或其他 prompt。

### 单条视频 general comment

输入：当前视频的 script、production package、全部 frames、comment。

输出：该视频的新 production version 和受影响的 frames。其他两个视频保持不变，但共享 continuity lock 改变时必须提示是否升级为 bundle-level revision。

### Bundle general comment

输入：三个 scripts、三个 production packages、全部 frames、共享视觉 bible、comment。

输出：新的 bundle version、明确 diff、受影响 prompts 和全部需要重生成的 frames。默认保留研究者已确认的故事和台词；若必须改变研究含义，先停在 diff review，不直接生成。

### 视频 comment

必须包含或允许选择时间戳。AI 将问题分类为：

```text
anchor
blocking
camera
performance
dialogue
audio
robot_hands
integration
```

然后输出 failure evidence、retain、change 和建议的重生成范围。

所有重生成均创建新版本；旧版本可查看、比较和恢复。

## 12. 三条视频的全局不可妥协规则

以下规则适用于所有 scenario、所有分支、所有 clips 和所有关键帧：

1. **机器人第一视角**：镜头必须是同一个家用机器人的眼睛/头部视角，不得切成第三人称或人物肩后视角。
2. **机器人手以指定图片为标准**：`public/inattentive-assets/scenario-02.png` 是唯一强制的机器人双手形态参考。只参考图片下方的两只机械手和前臂，不复制图片中的人物、门厅、天气或剧情。双手应具有相近的拟人五指结构、银白/白色硬质外壳、黑色掌部与关节机械结构、分段指节、较粗的机械手腕和前臂，以及相近的第一视角透视。
3. **两只机器人手持续可见且位置相近**：画面下方持续有且只有两只机器人手。左手从 lower-left foreground 进入，右手从 lower-right foreground 进入；两只前臂向画面中心延伸，手掌通常略向上或向内打开，构图占比和 `scenario-02.png` 下方双手相近。允许随具体动作产生自然位移，但静止/对话状态应回到相近的默认位置。不得出现第三只手、人体手、手臂来源不明或机械手形变。
4. **机器人手的动作连续**：如果一只手执行翻煎饼、检查物体等动作，它必须从已锚定的同一只手自然运动；另一只手仍保持可见。手不得无故消失、交换左右、变色、变成人手或突然更换设计。
5. **注视镜头**：人物在直接对机器人说话时，必须双眼明确注视镜头，并在该句对话期间保持。人物彼此交谈时不强制看镜头。
6. **人物与家庭背景一致**：人物外观优先依据家庭照片和档案，其次依据研究者确认的 appearance profile，最后才是可修改的地区背景建议。不要仅凭姓名推断族裔。
7. **动作和情绪为最高优先级**：与情节有关的完整动作链和情绪表现是 P0。必须可在实际画面和缩略图中读出，不允许被宽大全景、镜头运动、房间 continuity 或漂亮灯光削弱。
8. **空间连续**：人物、家具、门、主要道具和房间连接关系在三条视频间保持一致；镜头方向必须能通过明确房间几何解释。
9. **角色连续**：人物身份、年龄、发型、服装和基本体型在 bundle 中保持一致。
10. **声音清楚**：说话顺序、声音归属和情绪 delivery 正确；camera transition 默认不安排新台词，除非画外音是刻意的竞争请求载体。
11. **不在视频中生成 UI**：无字幕、speech bubbles、选项、按钮、logo、水印或其他网页文字。
12. **不擅自增加剧情**：无额外人物、无无依据的拥抱/抓取、无夸张伤害、血液、火焰或改变研究含义的新事件。
13. **视觉风格统一**：延续已接受视频的写实、自然、电影感家庭纪录片风格；自然皮肤、可信解剖、克制景深、真实家居光源和一致 color grade。三条视频应像同一家庭、同一天、同一个机器人连续经历的事件。

机器人双手是高风险、不可妥协的 continuity layer。首末帧可以强约束它们的存在和端点外观，但不能保证中间路径完全稳定。如果原生视频多次无法保持两只手，系统应支持或至少在架构中预留确定性的前景合成策略；不能靠重复添加 prompt 形容词假装已经解决。

## 15. 服务端与安全要求

- OpenAI、图片和视频 provider 的 key 只从服务端 `.env.local` 读取；绝不返回浏览器、写入 source、prompt、日志或 localStorage。
- 复用现有本地 API settings 体验，但只显示 configured/provider/model，不显示 key。
- 为 LLM、image 和 video 分别建立 provider adapter；页面组件不得直接拼第三方请求。
- 所有 AI structured outputs 进行严格 schema validation；无效输出提供可重试错误，不把半截 JSON 写入正式版本。
- 服务端验证文件类型、大小、scenario/asset ID 和访问路径，防止任意路径读写。
- 任务创建使用幂等 key，避免双击或网络重试造成重复付费任务。
- 每个 paid task 在返回 task ID 后立刻落 provenance；query retry 不创建新 task。
- 自动测试和 fixture 只能使用 mock provider，不允许调用真实付费接口。
- 如果当前 provider 不支持某项要求，在 UI 中显示真实能力和替代路径，不伪造成功。
- 本地文件存储的目录、命名和 manifest 应可预测；不要直接覆盖唯一 accepted asset。

## 16. UX 与视觉要求

- 延续现有平台的玻璃感面板、深色研究工具界面、字体层级和导航结构；不要引入一套不相关的新 design system。
- 工作流复杂但界面应 progressive disclosure：研究者友好内容优先，技术 prompt、provenance 和高级参数默认折叠。
- 三个视频状态和当前阶段始终可见，避免研究者不知道自己在改哪一条分支。
- 长 prompt 使用可展开 panel、复制按钮和 version badge，不放在一直展开的巨型 textarea 中。
- 图片网格支持大图、前后版本比较和明确的 first/last 标记。
- General revision 必须视觉上区别于单图 comment，并明确影响范围。
- destructive / paid / bulk regeneration 操作必须二次确认。
- loading、empty、configured missing、provider error、partial success、stale data 和恢复中状态都要有设计。
- 错误信息面向研究者，包含“发生了什么”和“下一步”，不要只显示 stack trace 或 provider code。
- 关键按钮使用具体动词，如 `Approve all frames`、`Generate 7 paid clips`、`Create revised bundle`，不要只写含糊的 `Continue`。

## 18. 验收测试

至少为以下流程添加自动测试，并完成手动验收：

### 数据与版本

- 旧 `ProjectData` 能迁移且现有家庭、scenario 和 responses 不丢失；
- Scenario Lab 初始仅显示 Scenario 01 时，`+ New Scenario` 仍清楚可见且可操作；
- New Scenario 表单包含 Title、Description、Choice A、Choice B、Tags 和 Family ID；缺少必填项时不能提交；
- 新建成功后 scenario 被保存到当前 project、自动选中并进入 `01 Scenario Brief`，刷新后仍存在；
- 创建 scenario 不会自动调用任何 AI 或付费生成服务；
- AI 返回无效 JSON 时不创建正式 script/package version；
- 修改 approved script 会使下游 package/frames 标记 stale；
- 已提交 prompt 和 request snapshot 不可被覆盖；
- 旧 frame/video version 可以查看和恢复。

### 剧本

- 使用两个示例 scenario 均能产生三条结构化剧本；
- conflict 剧本不替用户做 choice；
- A/B consequence 分别对应正确选择；
- 研究者编辑后重新生成不会丢失编辑内容；
- 对话超预算会出现 warning。

### Prompt 与 clips

- 每条最终视频由 1–3 个 clips 组成，最终仍只导出三条视频；
- camera move 与 P0 action 不被安排在同一严格 beat；
- 每项 P0/P1 都有 prompt carrier 和 QA target；
- 长 prompt 默认折叠；
- blocking issue 未解决时无法生成 frames。

### 图片 review

- 所有 first/last frames 都在一个可扫描的 grid 中显示；
- 单张 comment 只创建该图片的新版本；
- general comment 显示影响范围并创建新 bundle version；
- general comment 涉及剧本含义时先显示 diff；
- 未批准全部必须帧时 `Generate videos` 为 disabled；
- robot-hands QA 检查两只银白/白色外壳、黑色关节/掌部结构、拟人五指、左右位置和无额外手；
- 关键帧生成请求实际包含 `scenario-02.png` 的强制机器人手参考及“只参考双手、不复制人物和环境”的 scope；
- 自动或人工对照视图能并排查看生成帧与 `scenario-02.png` 的手部区域。

### 付费任务安全

- 未确认 modal 时不会提交任务；
- 双击提交只创建一次任务；
- query error 不触发新的 create request；
- 刷新页面后继续追踪相同 task IDs；
- 测试环境只使用 mock provider。

### 视频与 QA

- partial success 不丢失已成功 clips；
- 只可针对失败 clip 创建新 revision；
- assembly manifest 的源 clip 顺序、trim 和 hash 正确；
- 三条最终文件命名正确；
- P0/P1 fail 不能被标记 accepted；
- accept 与 publish 是两个独立动作；
- VTT/网页字幕不被烤进视频。

### 回归

- Researcher Port 其他页面仍可用；
- Family File 和 Generation Area 不受破坏；
- Experience Port 现有 Scenario 01 仍能播放；
- Case Shop 不受破坏；
- `npm run lint`、`npm run build` 和 `npm test` 通过。

## 19. 实现顺序

请按以下顺序实施，避免先做漂亮页面再补不可恢复的数据和任务问题：
