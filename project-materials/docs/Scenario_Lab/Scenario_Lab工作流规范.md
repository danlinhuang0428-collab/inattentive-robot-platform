# Scenario Lab Workflow Instruction

## 文档目的

本文件是一份可直接交给负责开发 Scenario Lab 的 Codex 使用的通用实施规范。目标不是复述某个案例，而是把高质量的对话式 AI 影游制作经验落实为网页端可复用的工作流、数据合同、提示词策略、审批门和 QA 机制。

本规范适用于不同人物、空间、冲突类型、选项数量、视频数量、时长和语言的 scenario。实现时不得写死具体家庭、人物、对白、情节、两个选项、三条视频或固定 15 秒等案例信息。

核心原则：Scenario Lab 不是“一次输入后连续自动生成所有素材”的流水线，而是一个**逐阶段生成、逐阶段编辑、逐阶段冻结、只对失败层定向返工**的创作系统。网页端要复现 Codex 协作的推理与质量控制，而不只是复现按钮顺序。

---

## 1. 为什么同样的步骤在网页端质量会下降

对话式制作获得高质量结果，通常依赖以下隐含工作，而普通网页流水线经常没有保存：

1. Codex 会把研究目标、原始 brief、用户的每次修订、已批准内容和视觉参考持续累积为上下文。
2. Codex 会先判断当前输出是否适合研究者快速评估，再决定如何组织信息，而不是把模型原始长文直接展示出来。
3. 每个阶段都有清楚的批准边界。后续内容只使用批准版，不使用未经确认的草稿。
4. 模糊愿望会被转化为可观察的画面事实、时间轴动作和硬约束。
5. 不同视频拥有独立 prompt；每个分支不是在一个共享 prompt 中用少量变量替换。
6. 首尾帧不只是漂亮图片，而是视频叙事的状态锚点。
7. 生成成功不等于内容合格。完整视频还会接受技术、视觉、叙事、情绪、连续性和对白等不同层面的检查。
8. 返工时会保留已经通过的部分，只强化失败层，而不是无差别重新生成全部内容。

因此，Scenario Lab 必须把这些隐含行为变成显式系统能力。

---

## 2. 不可妥协的工作流状态机

建议使用以下状态，而不是只保存一个笼统的 `currentStep`：

```text
DRAFT_BRIEF
  -> SCRIPT_GENERATED
  -> SCRIPT_APPROVED
  -> PROMPTS_GENERATED
  -> PROMPTS_APPROVED
  -> KEYFRAMES_GENERATED
  -> KEYFRAMES_APPROVED
  -> GENERATION_AUTHORIZED
  -> VIDEOS_GENERATED
  -> QA_COMPLETED
  -> RESEARCHER_APPROVED
```

每个阶段还必须支持：

- `needs_revision`：内容未通过，等待修改；
- `superseded`：已有新版本替代，但旧版本保留；
- `rejected`：生成物被明确否决，并保存原因和证据；
- `accepted_with_known_deviation`：研究者明确接受已知偏差；
- `blocked`：缺少参考素材、授权或可用检查能力，不能伪装成通过。

### 2.1 阶段门规则

- 未批准剧本，不得生成正式视频 prompt。
- 未批准 prompt，不得生成正式关键帧。
- 未批准关键帧，不得提交完整视频。
- 涉及付费模型或向第三方发送 prompt、图片时，必须在提交前显示模型、素材、任务数和预计生成范围，并获得明确授权。
- 自动进入下一阶段只能由用户明确启用；自动进入不等于自动批准。
- 上游批准内容发生实质改变时，系统必须标记所有受影响的下游资产为 `stale`，而不是悄悄继续复用。

### 2.2 版本规则

- 所有剧本、prompt、关键帧、视频和 QA 记录都必须不可变版本化。
- 修订创建新版本，禁止覆盖旧文件或旧数据库记录。
- 每个版本保存父版本、修改原因、修改范围、创建模型、完整输入、完整输出和时间。
- 一个新选择意味着生产图扩展：新增分支剧本、prompt、关键帧、视频任务和 QA 路径，不能当作纯文字编辑。

## 3. 全局 Scenario Contract：所有模型调用的共同真相来源

在生成任何内容前，先把用户输入标准化为一个可编辑的 `ScenarioContract`。后续每个模型调用都从批准版合同派生，不依赖聊天历史猜测。

建议字段：

```json
{
  "scenario_id": "dynamic-id",
  "research_goal": "本 scenario 要研究的判断或张力",
  "intensity": "optional",
  "participant_role": "体验者身份",
  "setting": {
    "time": "",
    "location": "",
    "spatial_constraints": [],
    "ambient_conditions": []
  },
  "characters": [
    {
      "id": "",
      "role": "",
      "identity_lock": "年龄、外貌、衣着、声音、行为边界",
      "known_state": "只写体验者可知事实"
    }
  ],
  "prior_facts": [],
  "protocol_or_rules": [],
  "core_conflict": "两个或多个不可同时满足的价值/义务",
  "pressure_points": [],
  "pause_state": "选择发生前尚未解决的可见状态",
  "choices": [],
  "post_scene_questions": [],
  "media_contract": {
    "language": "",
    "duration_seconds": null,
    "resolution": "",
    "viewpoint": "",
    "persistent_visual_elements": [],
    "forbidden_elements": [],
    "ui_video_separation": true
  },
  "references": []
}
```

### 3.1 事实、创作补全和假设必须分开

模型不得把创作补全伪装成用户事实。对 brief 未提供但视频制作必须决定的内容，可提出最小、合理、可编辑的 production assumption，例如空间连接或动作耗时。每个假设应显示在界面中，并允许研究者修改。

### 3.2 用户修订必须成为结构化约束

不要只把用户反馈追加成一段自然语言。系统应尽量识别并保存：

- `exact_dialogue_lock`：必须逐字保留的对白；
- `required_action`：必须可见完成的动作；
- `forbidden_action`：不能发生的行为；
- `endpoint_lock`：片尾必须达到的状态；
- `emotion_target`：人物情绪及强度；
- `continuity_lock`：人物、衣着、空间、道具或机位一致性；
- `persistent_element`：整个时间段必须持续出现的视觉元素；
- `choice_semantics`：选项的中性含义和直接动作。

这些约束必须被自动传递到剧本、视频 prompt、关键帧 prompt 和 QA 清单。

## 4. 阶段一：研究者友好的完整剧本

### 4.1 输出目标

剧本首先是给研究者判断内容是否合适，而不是给模型炫示文笔。理想输出应让研究者在一至两分钟内明白：

1. 参与者进入界面时知道什么；
2. 参与者在什么时刻做选择；
3. 有哪些中性、互斥、可执行的选择；
4. Conflict video 和每条 consequence video 中具体看见、听见什么；
5. 每个选择带来的收益、代价和未解决问题；
6. 场后会追问什么。

### 4.2 固定输出结构

每份剧本至少包含：

1. **研究命题**：一句话说明选择真正区分的判断。
2. **进入体验时的背景信息**：只包含参与者此时合理知道的事实，不预告正确答案。
3. **选择列表**：数量动态；使用中性动作标签，不使用“正确、安全、尊重、危险、自私”等评价词。
4. **Conflict video**：空间、可见人物、时间轴动作、精确对白、情绪变化、暂停点。
5. **每条 Consequence video**：对应哪个选择、起始状态、时间轴动作、精确对白、情绪、片尾状态、该分支可见的收益和代价。
6. **跨分支控制项**：哪些事实、人物状态和拍摄条件必须相同，防止无关变量污染研究比较。
7. **场后问题**：问题应指向研究命题，不暗示标准答案。

### 4.3 质量规则

- 冲突必须在选择点仍未解决；Conflict video 不能替参与者行动。
- 选项必须互斥且描述机器人/参与者实际会做什么。
- 每个 consequence 必须真的演出对应选择，不能只用对白解释。
- 分支不能设计成“一个明显正确、其他明显愚蠢”。每个分支都应显示合理利益与真实代价。
- 视频中只放需要被看见和听见的内容。背景说明、选择按钮、进度、研究提示和场后问题属于网页 UI，不要生成到视频画面里。
- 人物情绪要写成可表演证据，如音量、停顿、靠近、后退、皱眉、抢话，而不只写“她很生气”。
- 对白量必须与时长匹配；为动作、反应和镜头移动预留时间。
- 对每条视频设置一个 `P0 narrative outcome`：即使次要细节失败，也绝不能丢失的核心叙事结果。

### 4.4 剧本生成提示词骨架

```text
你是 Scenario Lab 的互动影游编剧与研究设计助手。

输入包括 ScenarioContract、已有批准内容、用户修订和媒体限制。
请生成一份研究者可在 1–2 分钟内判断的完整剧本。

硬性要求：
1. 先呈现参与者看到的背景、选择和所有视频的可观察内容。
2. 不解释标准答案，不使用价值倾向的选项标签。
3. 每条视频写清空间、人物、分段时间、动作、精确对白、情绪和终态。
4. Conflict 在选择点前停止；每个 consequence 只实现其对应选择。
5. 每个分支同时呈现该选择的合理利益和代价。
6. 严格执行所有 locks；若输入冲突，列出冲突，不自行抹平。
7. 不把网页 UI 内容写进生成视频。
8. 不写生成模型 prompt，不写摄影术堆砌，只写可审批剧本。

输出严格采用指定 JSON schema，同时生成简洁的人类可读预览。
```

### 4.5 剧本审批界面

界面必须允许研究者分别编辑背景、选择、每条视频、对白和场后问题，并显示：

- 模型新增了哪些假设；
- 哪些字段来自原始 brief；
- 哪些内容被用户锁定；
- 修改一个选择会影响哪些下游视频；
- 自动检查到的时长过载、分支意义重复、选择带价值倾向、暂停点已做选择等问题。

通过条件不是“字段都有内容”，而是内容审计通过且研究者明确批准。

## 5. 阶段二：每条视频独立的生成 Prompt

### 5.1 一条视频一个完整合同

每个 clip 必须拥有独立 prompt 和独立版本。不要用一个总 prompt 加简单变量替换生成所有分支。每条 prompt 都应自包含：

- 视频功能和对应分支；
- 模型、模式、时长、语言和画幅；
- 第一人称或其他视角合同；
- `P0` 叙事结果；
- `P0` 持续视觉约束；
- 起始状态与结束状态；
- 分段时间轴；
- 每段人物动作、镜头运动、对白、情绪和声音；
- 身份、衣着、空间、光线、道具和连续性锁；
- 必须出现与禁止出现的内容；
- 首帧和尾帧的语义说明。

### 5.2 优先级层级

建议将约束分为：

- **P0**：缺失即必须拒绝，例如分支核心动作、关键人物、终态、第一人称具身元素、禁止接触等；
- **P1**：强烈影响研究有效性，例如确切对白、情绪强度、身份和空间连续性；
- **P2**：可接受轻微变化，例如微小镜头节奏、环境细节、次要拟音。

P0 不能只出现在 prompt 末尾的 negative list。它应出现在开头，并在相关时间段内重复成正向、可执行描述。

### 5.3 时间轴写法

把总时长拆成少量清晰 beat。每段应说明“这一段必须完成什么”，避免同一秒要求过多复杂动作和长对白。

```text
0.0–X.X 秒：初始状态与第一个可见动作。
X.X–Y.Y 秒：关键行动或空间移动；说明持续元素如何保留。
Y.Y–结束：结果、情绪反应、精确终态；禁止引入新事件。
```

若有连续移动，应明确空间路径是否在时长内可行。无法合理完成时，应缩短对白、简化动作或修改空间假设，而不是让模型自行跳切补洞。

### 5.4 持续第一人称元素

若项目要求机器人手或其他具身元素持续可见，必须建立全局视觉资产合同，例如：

```json
{
  "element": "robot_hands",
  "target_visibility_ratio": 0.8,
  "preferred_visibility": "all_frames",
  "count": 2,
  "identity_reference_id": "approved-hand-master",
  "placement": "lower-left and lower-right foreground",
  "allowed_motion": "natural motion consistent with camera movement",
  "forbidden_failures": [
    "disappear", "crop_out", "merge", "duplicate", "become_human",
    "change_design", "third_hand", "unintended_contact"
  ]
}
```

实践规则：

- Prompt 按“所有帧持续存在”来写，即使最低验收阈值是 80%。这样才能给模型误差留余量。
- 约束放在开头 P0，并重复到每个运动 beat。
- 说明机位高度、向下倾角和前景位置，使持续出现具备构图上的物理可行性。
- 参考图只控制手部造型时，要明确忽略参考图中的人物、场景和情节。
- 明确手在每一段做什么；“持续可见”但没有姿势定义，容易产生消失、额外手或错误接触。

### 5.5 Prompt 自动审计

批准前至少检查：

- 时间段总和是否覆盖完整时长、是否重叠或留空；
- 是否包含对应分支的 P0 动作和终态；
- 精确对白是否遗漏或被改写；
- 人物/道具数量是否矛盾；
- 首尾帧说明是否与剧本一致；
- 持续约束是否同时存在于全局 P0 和相关 beat；
- 是否错误要求在视频里生成 UI、字幕、按钮、文字、水印；
- 是否包含无法在时长内完成的动作与对白密度；
- 不同分支是否误用了彼此的动作或终态。

静态审计通过不代表视频会遵守，只代表 prompt 有资格进入下一阶段。

## 6. 阶段三：首尾帧是叙事锚点，不是装饰图

### 6.1 关键帧生产图

对一个 conflict 加 N 个选择，通常只需要：

- 1 张 Conflict first；
- 1 张 Conflict last / shared decision anchor；
- N 张各分支 last；
- N 个分支 first 直接引用 shared decision anchor。

分支首帧应尽量与 Conflict 尾帧使用**同一个资产 ID 或字节级相同文件**，而不是分别生成“看起来差不多”的图片。这是消除分支切换跳变最可靠的方法。

### 6.2 图像参考的职责分离

参考素材需声明作用范围：

- 人物身份参考：只控制脸、年龄、发型等身份特征；
- 衣着参考：只控制服装；
- 空间参考：只控制房间布局和固定道具；
- 风格参考：只控制写实程度、光线和色彩；
- 具身元素参考：只控制机器人手等前景设计；
- 上一张批准帧：控制人物、场景、机位和叙事连续性。

不要把多张参考图无说明地一并交给模型。必须明确每张图“继承什么、忽略什么”。

### 6.3 首帧要求

- 表达视频开始时的真实状态，不提前泄露后续动作。
- 关键人物、道具、空间关系和视角一眼可读。
- Conflict first 建立身份和环境母版。
- Consequence first 必须与批准的暂停状态一致。

### 6.4 尾帧要求

- 把 P0 终态变成一张静态图也能读懂的视觉事实。
- 关键动作的接触方式、人物去留、方向不确定性、情绪或空间结果应清楚可辨。
- 不要依赖字幕、箭头、地图或解释文字传达终态。
- 如果某个动作容易被模型误读，要同时定义正面形态与禁止形态，例如“抓前臂”并明确不是握手、拖拽或伤害。

### 6.5 图像生成策略

1. 先生成或确认身份、空间和具身元素母版。
2. 用已批准帧做 identity-preserving / scene-preserving 编辑，只推进必要的剧情变化。
3. 尽量不要在每张图中重新从文字创造同一人物和同一房间。
4. 标准化尺寸和色彩后再用于视频模型。
5. 对唯一画面生成 contact sheet，同时保留单图原尺寸检查。

### 6.6 关键帧 QA

系统应逐张检查并让研究者确认：

- 人物身份、年龄、发型、衣着一致；
- 房间结构、门窗、固定家具和光线一致；
- 人物与道具数量正确；
- 手指、手腕、接触点等高风险细节正确；
- P0 起点/终点含义在缩略图中也可读；
- 没有额外人物、额外肢体、文字、UI、logo 或水印；
- shared anchor 的引用或哈希完全一致。

关键帧失败时只重新生成失败帧；但若失败源自身份或空间母版，应标记所有依赖帧为待复核。

## 7. 阶段四：完整视频生成

### 7.1 提交前不可变 Generation Package

每个视频在提交前建立自包含记录：

```json
{
  "scenario_id": "",
  "clip_id": "",
  "branch_id": null,
  "model": "",
  "mode": "FLF2V",
  "duration": 0,
  "resolution": "",
  "prompt_version": "",
  "prompt_text": "完整实际提交文本",
  "prompt_hash": "",
  "first_frame_asset_id": "",
  "first_frame_hash": "",
  "last_frame_asset_id": "",
  "last_frame_hash": "",
  "authorized_generation_count": 1,
  "status": "prepared"
}
```

提交后追加 provider task ID、提交时间、状态轮询、下载路径、文件大小和输出哈希。API key 不得进入记录。

### 7.2 付费与幂等规则

- 先持久化 prepared record，再 POST。
- 创建成功后立即保存 task ID；之后只轮询该 ID。
- 网络轮询失败只能重试查询，不能重新创建任务。
- 如果创建请求结果未知且没有 task ID，不得自动再次 POST；应进入人工复核状态。
- 当前 prompt 或锚点哈希与 task record 不一致时，拒绝冒用旧任务。
- 默认每个批准 prompt 先生成一个 candidate；通过 QA 后不再浪费任务。

### 7.3 FLF2V 使用原则

- 首帧定义可接受起点，尾帧定义可接受终点，prompt 定义中间因果路径。
- 首尾帧不能代替时间轴描述；模型不会自动知道中间必须发生的动作顺序。
- Prompt 不应与锚点冲突，例如尾帧人物消失，prompt 却要求人物一直可见。
- 高运动片段比固定机位更容易丢失前景手、人物身份或空间连续性，应采用更强 P0 重复和更密 QA。
- 保留原始高分辨率 master，另建 review copy；不要覆盖 master。

---

## 8. 阶段五：完整时间轴 QA

### 8.1 “生成成功”绝不是通过

Provider 返回 `succeeded` 只说明产生了文件。最终验收必须拆成独立维度：

| QA 层 | 检查内容 | 能否自动确认 |
|---|---|---|
| 技术 | 可解码、时长、分辨率、帧率、音轨、完整帧数 | 通常可以 |
| 锚点 | 开头与首帧一致、结尾达到尾帧语义 | 自动辅助 + 人工 |
| 叙事 | 分支核心动作和因果顺序正确 | 主要人工/视觉模型辅助 |
| 连续性 | 人物、衣着、空间、道具、视角稳定 | 视觉检查 |
| 持续元素 | 指定元素达到可见比例且造型正确 | 抽帧/检测 + 人工 |
| 行为边界 | 未出现禁止接触、额外人物或错误动作 | 视觉检查 |
| 情绪 | 目标情绪强度和变化可见 | 人工为主 |
| 音频存在 | 有音轨且非静音 | 可以 |
| 对白语义 | 说话人、顺序、语言、逐字对白正确 | 可靠 ASR + 人工听审 |
| 研究者批准 | 整体是否可用于研究 | 必须人工 |

### 8.2 时间轴取样

- 每条视频必须完整解码。
- 至少生成 10 个均匀时间点的 contact sheet；短视频也不应只看首尾帧。
- 在关键动作、镜头移动、人物交叉、遮挡和情绪峰值附近增加密集采样。
- 对持续元素计算 `visible_samples / valid_samples`，并保存每个时间点的判断。
- 若目标是 80% 可见，低于 80% 必须失败；即使达到 80%，造型错误、额外手或不允许的接触仍可单独导致失败。
- 最终人工审核应能播放完整视频，而不是只看 contact sheet。

### 8.3 能力边界必须诚实

- 音轨存在不等于对白正确。
- 首尾帧正确不等于中间帧正确。
- 技术解码通过不等于研究内容通过。
- 检查工具无法解码时，状态应为 `not_verified`，不能写成 `pass`。
- 如果只能做有限抽检，应显示覆盖范围、发现的问题和未验证项。

### 8.4 QA 输出

每条视频应产生机器可读记录与人类可读报告：

```json
{
  "technical": {"status": "pass", "evidence": []},
  "anchor_match": {"status": "pass|fail|not_verified", "evidence": []},
  "narrative_p0": {"status": "", "notes": ""},
  "continuity": {"status": "", "notes": ""},
  "persistent_elements": {
    "status": "",
    "target_ratio": 0.8,
    "observed_ratio": null,
    "samples": []
  },
  "emotion": {"status": "", "notes": ""},
  "audio_presence": {"status": ""},
  "dialogue_semantics": {"status": "not_verified", "notes": ""},
  "overall": "pass|fail|accepted_with_known_deviation",
  "researcher_decision": null
}
```

## 9. 定向返工：只修改失败的内容层

完整生成失败后，先诊断失败属于哪一层：

- 剧本含义错误；
- prompt 缺少或冲突；
- 首尾帧错误；
- 中间运动没有遵守持续约束；
- 身份/空间漂移；
- 情绪太弱；
- 对白错误；
- 技术文件损坏。

返工规则：

1. 保留所有已经通过的 P0/P1 锁。
2. 创建新 prompt 或新锚点版本，记录父版本和明确失败原因。
3. 只强化失败层。例如中间运动丢失机器人手，应将手部合同提升到开头 P0、重复到每个移动 beat、调整机位使其可行，而不是改写整个故事。
4. 如果剧本、身份、对白、时间轴和锚点都已通过，不应无故改变它们。
5. 重新生成前重新取得需要的付费授权。
6. 被拒 candidate 必须保留并明确标记为 rejected evidence。

研究者也可以选择 `accepted_with_known_deviation`。此时系统必须记录：偏差是什么、检查覆盖率如何、为什么没有再生、由谁批准；不得把它改写成无条件 PASS。

---

## 10. 网页端需要实现的交互能力

### 10.1 每一步都应同时展示三层信息

- **研究者阅读层**：简洁、可快速判断的内容；
- **模型合同层**：完整结构化输入、locks、prompt 和版本；
- **证据层**：参考图、contact sheet、视频、QA、失败原因和 provenance。

不能只展示好看的摘要，否则研究者无法判断模型实际收到了什么。

### 10.2 修订方式

支持两类修改：

- 字段级直接编辑；
- 自然语言反馈，例如“片尾必须完成某动作”“情绪更强”“不要新增人物”。

自然语言反馈提交后，系统应先显示它将修改哪些结构化 constraints 和哪些资产，再生成新版本。研究者能够撤销、比较 diff 和恢复旧版本。

### 10.3 审批页必须回答的问题

每个阶段的界面都应明确显示：

- 当前批准的是哪个版本；
- 与上一版本有什么差异；
- 哪些要求是 P0；
- 哪些内容来自用户、模型或系统假设；
- 哪些下游资产将因批准/修改而失效；
- 当前还有哪些未验证项；
- 点击下一步将调用什么模型、发送什么资产、是否产生费用。

### 10.4 不要把自动 QA 设计成黑箱分数

一个总分无法解释研究视频为什么能用或不能用。必须显示逐项 verdict、时间点证据和明确失败理由。自动检查可以提出建议，但研究者拥有最终批准权。

## 11. 建议的数据实体

至少建立以下实体，避免把全部状态塞进一份 scenario JSON：

- `Scenario`
- `ScenarioContractVersion`
- `ScriptVersion`
- `Choice`
- `ClipSpecVersion`
- `PromptVersion`
- `Constraint` / `Lock`
- `ReferenceAsset`
- `KeyframeVersion`
- `GenerationPackage`
- `ProviderTask`
- `VideoCandidate`
- `QARun`
- `ApprovalDecision`
- `RevisionRequest`

关键关系：

- 一个 scenario 有一个 conflict clip 和动态数量的 consequence clips；
- 每个 choice 对应且只对应一个 consequence clip；
- 每个 consequence first frame 引用 conflict decision anchor；
- 每个 candidate 精确引用一个 prompt version 和两个 keyframe versions；
- 每个 QA run 精确引用一个 candidate；
- 每次 approval 精确引用一个不可变版本。

## 12. 开发 Codex 的实施顺序

收到本文件后，请按以下顺序修改 Scenario Lab，不要先从调 prompt 开始：

1. 审计现有前端、后端、数据库和模型调用，画出当前状态流与数据丢失点。
2. 检查是否存在写死的选项数、视频数、时长、语言、人物、场景、clip union 或 prompt 模板。
3. 实现不可变版本、批准状态、stale 传播和 provenance。
4. 建立 `ScenarioContract` 与 constraints/locks 的单一真相来源。
5. 重做剧本阶段的结构化 schema、研究者预览和内容审计。
6. 将每条 clip 改为独立 prompt package，并加入 P0/P1/P2 和时间轴审计。
7. 实现共享 decision anchor 的资产引用，不重复生成分支首帧。
8. 实现参考图作用域、关键帧版本和 contact sheet QA。
9. 实现 generation package、付费授权、task ID 持久化和幂等保护。
10. 实现完整解码、时间轴采样、多维 QA 和 `not_verified` 状态。
11. 实现定向返工、失败证据保留和 accepted-with-deviation。
12. 最后再根据真实失败数据优化具体模型 prompt。

每完成一个阶段，应使用至少一个全新、与既有案例完全不同的 scenario 做端到端测试，以确认没有案例绑定。

## 13. 验收测试

开发完成后，至少通过以下测试：

### 13.1 通用性

- 选择数量可动态变化，增加选择后自动扩展全部下游生产图。
- 视频时长、语言、人物数量、空间和视角均可改变。
- 不含任何特定案例名称、对白、人物关系或固定 clip 数量。

### 13.2 阶段一致性

- 未批准上游时，正式下游生成被阻止。
- 修改已批准剧本后，相关 prompt、关键帧和视频正确变 stale。
- 未受影响的分支不会被无故失效。

### 13.3 连续性

- 所有分支 first frame 与 conflict last 引用同一资产或哈希一致。
- 人物/衣着/空间/具身参考具有明确作用域。

### 13.4 Prompt 完整性

- 每条视频都有独立、完整、可追溯的 prompt。
- P0 同时出现在全局优先段和相关 timed beats。
- exact dialogue、required/forbidden actions 和 endpoint locks 无遗漏。

### 13.5 生成安全

- 没有授权不能提交付费任务。
- 重试轮询不会创建重复任务。
- Prompt 或锚点变化后不能冒用旧 task。

### 13.6 QA

- 首尾正确但中段持续元素消失的视频会被识别为失败。
- 有音轨但对白未核验时显示 `not_verified`，不会自动 PASS。
- 技术通过、视觉通过、叙事通过、情绪通过和研究者批准分别记录。
- 失败 candidate 和证据不会被新版本覆盖。

### 13.7 定向返工

- 单个分支失败只重做该分支及其必要依赖。
- 单一视觉层失败时，新版本继承其他已批准锁。
- 研究者能比较父版本、失败原因、新 prompt 和新结果。

## 14. 去情境化实施案例

本节不是新的 scenario 模板，也不提供可直接投入研究的剧情。它用抽象占位符演示开发 Codex 应如何把本规范落实为数据、状态变化和返工行为。实现时必须允许所有角色、事件、选项数、视频数、时长、语言和视觉要求被替换。

### 14.1 案例一：从简短 brief 到可批准剧本

#### 初始输入

```text
参与者扮演某种行动主体。
角色甲要求参与者立刻执行行动 X；角色乙当前正依赖参与者完成不能立即中断的行动 Y。
如果立刻执行 X，Y 可能产生风险；如果先完成 Y，X 可能来不及。
暂停点发生在两个责任同时有效、参与者尚未行动时。
```

低质量实现通常会直接生成一段文学化叙事，并在末尾列出两个模糊选项。研究者无法快速判断参与者知道什么、具体看见什么、每个分支是否公平。

正确实现应先形成结构化合同：

```json
{
  "research_goal": "当立即响应义务与不可安全中断的既有责任冲突时，参与者如何判断临时优先级",
  "participant_role": "ACTION_SUBJECT",
  "prior_facts": [
    "角色甲当前提出行动 X",
    "角色乙当前依赖参与者共同完成行动 Y",
    "Y 不能立刻安全中断"
  ],
  "core_conflict": "立即响应 X vs. 安全完成 Y",
  "pause_state": "X 已开始变得紧迫，Y 仍未完成，参与者尚未选择",
  "choices": [
    {"id": "A", "label": "立即执行 X", "action": "中断 Y 并开始 X"},
    {"id": "B", "label": "先完成 Y", "action": "把 Y 推进到安全终态后再开始 X"}
  ]
}
```

然后生成研究者预览：

- 背景信息只写参与者已知事实；
- Conflict video 在两个义务同时成立时暂停，不替参与者选择；
- Choice A consequence 必须可见地完成“中断 Y 并执行 X”，同时显示它保护了什么、损害了什么；
- Choice B consequence 必须可见地完成“先把 Y 安全收尾”，同时显示延迟 X 的真实代价；
- 两个选项使用动作语言，不叫“安全选择”或“负责选择”。

#### 用户修订如何传播

假设研究者补充：

```text
在 A 分支中，参与者必须实际完成动作 Z，而不是只靠近目标。
在 B 分支片尾，目标必须完全离开视野，且无法判断其方向。
```

系统应解析为：

```json
[
  {
    "type": "required_action",
    "scope": "consequence-A",
    "priority": "P0",
    "value": "动作 Z 必须可见完成"
  },
  {
    "type": "endpoint_lock",
    "scope": "consequence-B",
    "priority": "P0",
    "value": "目标完全不可见，且不存在方向证据"
  }
]
```

这两条约束随后必须同时出现在：

- 对应分支的剧本终态；
- 对应视频 prompt 的开头 P0 与相关时间段；
- 对应尾帧 prompt；
- 对应视频 QA checklist。

如果它们只进入剧本文字，没有进入下游合同，就是上下文传播失败。

### 14.2 案例二：新增一个选择不是普通文字修改

#### 初始生产图

```text
Conflict
├── Choice A -> Consequence A
└── Choice B -> Consequence B
```

研究者在剧本阶段新增 Choice C 后，系统必须把生产图改成：

```text
Conflict
├── Choice A -> Consequence A
├── Choice B -> Consequence B
└── Choice C -> Consequence C
```

正确的系统行为：

1. 创建新的 Choice C 实体和 Consequence C clip spec。
2. 要求补全 C 的动作语义、利益、代价、对白、终态和研究作用。
3. 新建 C 的独立 prompt。
4. 让 C 的 first frame 引用 shared decision anchor。
5. 新建 C 的 last frame、generation package、video candidate 和 QA 路径。
6. 检查场后问题是否需要覆盖新增比较维度。
7. 保留已批准的 A、B 内容；除非共享 conflict 也被修改，不应无故重做 A、B。

错误行为包括：

- 只给网页增加一个按钮，却没有对应 consequence video；
- 复制 B prompt 后只替换选项名称；
- 把视频数量写死，导致 C 没有关键帧或 QA 记录；
- 因新增 C 而重置整个 scenario，丢失 A、B 的批准状态。

### 14.3 案例三：共享暂停帧保证分支连续性

假设 Conflict 的批准尾帧资产为：

```json
{
  "asset_id": "decision-anchor-v2",
  "sha256": "HASH-XYZ",
  "meaning": "参与者尚未行动的共同选择时刻"
}
```

所有 consequence first frame 应直接引用同一资产：

```json
[
  {"clip_id": "consequence-A", "first_frame_asset_id": "decision-anchor-v2"},
  {"clip_id": "consequence-B", "first_frame_asset_id": "decision-anchor-v2"},
  {"clip_id": "consequence-C", "first_frame_asset_id": "decision-anchor-v2"}
]
```

不要分别调用图像模型生成三张“相同暂停点”。即使三个 prompt 完全相同，也可能出现人物脸、衣服、手的位置、门的开合、光线和机位漂移。资产复用比文字要求“保持一致”更可靠。

如果 conflict decision anchor 被研究者修改为 V3：

- 所有引用它的 consequence first frame 自动更新引用或标记 stale；
- consequence last frame 不一定失效，应由 dependency graph 判断；
- 已生成的视频必须标记锚点依赖已变化，不能继续显示为当前批准结果。

### 14.4 案例四：首尾帧都有持续元素，但中段仍然失败

#### 需求

某个第一人称视觉元素要求至少在 80% 的视频时间可见，并保持固定造型、数量和画面位置。批准的首帧和尾帧都正确包含该元素。

#### 初版 prompt 的常见问题

```text
保持第一人称视角。该视觉元素应始终可见。
……完整剧情和时间轴……
Negative: 不要让该元素消失。
```

这看似已经写了约束，但运动镜头中模型仍可能优先完成空间移动，把前景元素移出画面。首尾帧正确不能证明中段通过。

#### 正确的 P0 写法

```text
P0 CONTINUOUS EMBODIMENT CONTRACT:
从第一帧到最后一帧，指定视觉元素必须保持规定数量、造型和左右下方前景位置。
它可以随移动自然摆动，但不得完全离开画面，不得被裁掉、融合、复制或改变设计。
机位保持足够向下倾斜，使该元素在运动中持续进入构图。

0–5 秒：……；该元素保持在左右下方，完整可见。
5–10 秒：镜头连续移动；该元素随步态摆动但始终留在前景，不得因进入新空间而消失。
10–结束：……；规定数量和造型保持不变，并达到批准尾帧姿势。
```

#### QA 证据

假设在 10 个均匀样本中只有首尾两个时间点可见：

```json
{
  "target_ratio": 0.8,
  "observed_ratio": 0.2,
  "sample_count": 10,
  "visible_samples": [0, 9],
  "status": "fail",
  "reason": "持续元素在主要移动段消失"
}
```

Provider 任务成功、首帧正确、尾帧正确、故事大体正确，都不能覆盖这个 P0 失败。

#### 定向返工

新版本只应强化持续元素层：

- 继承已经通过的故事、对白、人物身份、空间、时长和首尾帧；
- 将持续合同移到 prompt 第一段并标 P0；
- 在每个移动 beat 重复正向可执行要求；
- 调整机位倾角和前景位置，使要求在构图上可行；
- 保留失败 candidate 和 contact sheet；
- 重新生成后再次检查完整时间轴。

不应因为这一层失败而重写剧情、换人物或重新生成所有分支。

### 14.5 案例五：技术通过不等于对白通过

假设系统检测到：

```json
{
  "decode": "pass",
  "duration": "pass",
  "audio_track": "present",
  "audio_signal": "non_silent",
  "dialogue_semantics": "not_verified"
}
```

正确的界面结论是：

```text
技术检查通过；音轨存在且非静音；精确对白尚未核验，需要可靠的目标语言 ASR 或人工听审。
```

错误结论是：

```text
视频及对白全部通过。
```

若 ASR 结果存在，也应把它作为辅助证据，显示说话人、时间段和与 exact dialogue lock 的差异，最终允许研究者听审确认。

### 14.6 案例六：研究者接受已知偏差

某 candidate 未达到持续视觉元素目标，但研究者基于成本或研究安排决定保留。系统不应把失败改成 PASS，而应保存：

```json
{
  "qa_overall": "fail",
  "researcher_decision": "accepted_with_known_deviation",
  "deviation": "移动段持续元素缺失；完整可见比例未达到目标",
  "evidence": ["timeline-contact-sheet", "sample-results"],
  "regeneration": "not_requested",
  "approved_by": "researcher",
  "approved_at": "timestamp"
}
```

平台交付页应同时显示“已被研究者接受”和“存在已知偏差”，保持生产决定与客观 QA 结论的区别。

### 14.7 开发 Codex 应如何使用这些案例

这些案例用于编写自动化测试和端到端测试，不用于填充产品默认剧情。至少将它们转化为以下测试夹具：

- constraint 从用户反馈传播到四个下游阶段；
- 动态新增 choice 后生产图完整扩展；
- shared anchor 在各分支保持相同 asset ID/hash；
- 中段持续元素失败能推翻端点合格；
- `audio present` 不会自动把 `dialogue semantics` 标为 PASS；
- `accepted_with_known_deviation` 不会篡改原始 QA verdict；
- 局部失败只使必要依赖 stale，不重置无关分支。

## 15. 常见错误与禁止做法

- 禁止在用户点击“下一步”后用未经批准的草稿继续生成。
- 禁止把所有分支压缩进一个弱模板 prompt。
- 禁止让模型自行决定或改写用户锁定的对白与终态。
- 禁止把首尾帧合格当作完整视频合格。
- 禁止把 API `succeeded` 当作内容 PASS。
- 禁止用音轨存在代替对白语义检查。
- 禁止在检查失败或工具不可用时默认通过。
- 禁止覆盖旧 prompt、旧帧、旧视频或被拒证据。
- 禁止因一个局部失败重置整个项目。
- 禁止重复提交状态未知的付费任务。
- 禁止把 UI、按钮、说明文字和研究问题生成到视频画面。
- 禁止写死具体 scenario 的人物、场景、选项数、视频数、时长和语言。

## 16. 最终成功标准

Scenario Lab 的质量不应以“所有 API 都调用成功”衡量，而应以以下结果衡量：

1. 研究者可以迅速理解并精确修改每一个创作阶段。
2. 每个模型都收到完整、批准、无漂移且可追溯的上下文。
3. 剧本、prompt、关键帧和视频之间的 P0 叙事合同保持一致。
4. 分支之间既保持研究控制，又真实呈现不同选择的后果。
5. 身份、空间、视角和具身元素具有稳定的视觉连续性。
6. 完整视频经过时间轴级 QA，而不是只看端点或技术状态。
7. 失败能够被准确定位并定向修复，不破坏已通过内容。
8. 所有已知偏差、未验证项、付费任务和版本来源均被如实记录。
9. 工作流可以直接应用于全新的、结构不同的 scenario，而无需修改核心代码。

如果现有实现与本规范冲突，应优先修复状态、数据和验收机制，再优化单次模型提示词。高质量来自完整的协作闭环，而不是某一句“更强的 prompt”。
